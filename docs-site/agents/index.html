AI agents

An AI agent can read your calendars and, if you allow it, add events. calsync has no AI in it. It offers its tools over MCP, so the agent you already use can call them, whichever one that is.

What an agent can do

calsync_status
List the calendars in the sync, and how the last sync went.
calsync_agenda
See every calendar as one list, with one row per real event. It says so when a calendar or an event couldn't be read.
calsync_check_event
Show how plain words would be read as an event. Adds nothing.
calsync_preview_sync
Count what a sync would change. Changes nothing.
calsync_add_event
Add an event. If syncing is on, it's copied to your other calendars straight away. If syncing is paused or was never started, it stays on one calendar until the next sync. Only with --allow-write.
calsync_sync_now
Run a sync now, if syncing is on. Only with --allow-write.

No tool can sign in, remove a calendar, start or resume syncing, or allow a mass delete. A sync run by a tool can remove a few copies whose original is gone, as any sync does. No tool returns a calendar ID, an account name, a token, a .ics link or a server's reply. When something fails, the tool gives one of a few fixed reasons, such as "not signed in" or "refused", and calsync run --dry-run may show you more. Tools do show the names you gave your calendars, so keep addresses out of those.

"Syncing is on" means you pressed Apply and keep syncing on the page. If you run calsync from cron or your own timer instead, calsync_sync_now refuses, and an added event is copied at the next run.

An agent on this machine

The agent starts calsync mcp itself and talks to it directly. No port, no token. For Hermes, an open source agent that runs on your own computer:

hermes mcp add calsync --command calsync --args mcp

For Claude Code:

claude mcp add calsync -- calsync mcp

Any other agent that takes an MCP command works the same way. With Docker, the command is docker exec -i calsync python calsync.py mcp.

Hermes doesn't pass your environment to the tools it starts. If you set CALSYNC_HOME or CALSYNC_TZ, add it to the command, before --args: --env CALSYNC_HOME=/your/folder CALSYNC_TZ=Area/City. Use one --env for all of them, because Hermes keeps only the last one. Without it the agent reads the wrong calendars, or none.

Let Hermes set it up

A skill teaches Hermes how to install calsync, open the setup page with you, connect these tools and use them. You still sign in yourself, and you start syncing yourself, on the page. The skill tells Hermes this, but Hermes can also run commands, so see the note below.

hermes skills install https://docs.getcalsync.app/hermes/SKILL.md

An agent on another machine

calsync mcp --http        # http://127.0.0.1:8485/mcp
calsync mcp token         # print the token the agent must send
calsync mcp token --new   # replace it; the old one stops working at once

Every request needs the token as Authorization: Bearer ..., and a page in a web browser can't call it. It listens on this machine only. To reach it from elsewhere, put it behind your own HTTPS proxy or a private network, and list the name in CALSYNC_HOSTS. Don't open the plain port to the internet: the token would travel unencrypted. Many agent platforms accept only an https:// address anyway.

mcp_servers:
  calsync:
    url: https://calendar.example.com/mcp
    headers:
      Authorization: Bearer ${CALSYNC_TOKEN}

With Docker, docker compose --profile agents up -d runs it beside the web page, read only, on 127.0.0.1:8485. docker compose exec calsync python calsync.py mcp token prints the token.

Choose how much it sees and does

--allow-write
Also offer the two tools that change calendars. Off unless you ask.
--busy-only
Show every event as Busy: times only, no titles or places. Enough for an agent that only finds free time. It can't be combined with --allow-write.

An event marked private always shows as Busy.

Before you connect one

These limits are on the tools, not on the agent. An agent that can also run commands on your computer, as Hermes normally can, runs as you. It could read calsync's data folder or run calsync purge without any of these tools. Read only stops it changing calendars by accident through calsync's tools. It isn't a wall. To make it one, turn off every agent tool that reaches your computer: shell, files, running code and sub-agents. Or run calsync under a different user and connect with --http, because a command the agent starts runs as the agent.

An agenda isn't proof you're free. An invite carrying calsync's own tag is treated as a copy and left out, and so are events titled "Cancelled:".

What an agent reads goes to whichever model it runs on, so your event titles go there too unless you use --busy-only.

Anyone can put an event on your calendar by inviting you, so an event title can be written to trick an agent. calsync keeps each title to one short line and tells the agent it is data, not instructions. That helps, but it can't guarantee what a model does. If you turn on --allow-write, use an agent that asks you before it adds something.
